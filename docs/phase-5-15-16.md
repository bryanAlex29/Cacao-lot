# Fases 5.15–5.16 — Gestión visual de equipos y parcelas propias

## Alcance autorizado

El usuario confirmó la revisión manual de 5.13/5.14 y autorizó avanzar con gestión mientras se ausentaba. Se implementaron dos incrementos sobre las API existentes, sin ampliar permisos ni implementar IA/clima.

### 5.15: dispositivos

- **Mis parcelas → Ver dispositivos y sensores**: ADMIN propietario puede registrar un equipo mediante serie, origen REAL/DEMO e intervalo esperado entero de 1–86400 segundos. DEMO solo se ofrece en desarrollo; el backend sigue aplicando `SourcePolicy`.
- El alta atómica existente crea seis identidades de sensor, no lecturas ni prueba de instalación/calibración. No inicia simulador ni cambia firmware.
- Confirmación obligatoria de parcela/origen y responsabilidad de guardar la clave. Solo se conserva en memoria el UUID y la clave devueltos por el alta; no se guardan en almacenamiento web, logs o documentos.
- La clave se puede seleccionar manualmente en un campo de solo lectura. Se elimina al pulsar **Ya guardé la clave · Ocultar**, cerrar el panel, cambiar parcela, salir o recargar. **Guardar antes de navegar**: no hay recuperación ni rotación de claves implementadas.
- Actualizar solo el inventario no destruye el panel de clave. Mientras se muestra la clave se bloquea otra alta.
- Fallos de red/timeout/5xx o respuesta incompatible se consideran resultado incierto: sin reenvío automático, formulario bloqueado hasta que el usuario declare haber revisado el inventario. Si el alta llegó al servidor pero la respuesta se perdió, la clave no se puede recuperar: no fabricar otra ni reutilizar la serie.
- Habilitación/deshabilitación con confirmación y cancelación explícitas. Solo envía `isActive`; un error obliga a reconsultar. No borra datos ni envía órdenes a válvula.
- No permite editar serie/origen/intervalo después del alta, borrar/reasignar equipos, provisionar para otras cuentas ni editar/calibrar sensores.

### 5.16: parcelas

- ADMIN propietario: **Editar parcela**, nombre/ubicación obligatorios, área positiva opcional que puede quitarse. Conserva el borrador ante fallo.
- **Archivar parcela** exige escribir el nombre exacto y una segunda confirmación. API existente con archivo lógico; conserva equipos, sensores y lecturas. Oculta la parcela y bloquea consultas/ingesta futuras; **no detiene físicamente el riego**.
- No se añade restauración, lista de archivadas o transferencia de propiedad.
- No hay versionado optimista en estas API: se advierte coordinar sesiones, sin prometer combinación de ediciones concurrentes.
- Una escritura sin confirmación se bloquea hasta actualizar explícitamente la lista. No se reintenta automáticamente.

## Permisos y límites

FARMER conserva creación de parcelas propias e inventario de solo lectura; no ve ni puede ejecutar las nuevas escrituras. ADMIN sigue sin acceso global. No se modifican roles de cuentas locales, rangos, calibraciones, márgenes, firmware, configuración privada, esquema o dependencias.

Implementar formularios no autoriza operar sobre recursos reales del usuario. Las pruebas crean/archivan exclusivamente recursos en bases temporales generadas por el runner; no se han registrado ni archivado equipos/parcelas en la principal.

## Validación

- 446 pruebas Angular, 209 backend, 151 integración PostgreSQL/Socket.IO, 34 Edge y 10 simulador: **850 pruebas** en las suites finales.
- Tipos, lint, build y smoke verificados. Angular se ejecuta con configuración serial externa temporal (`maxWorkers: 1`, `fileParallelism: false`), sin modificar timeouts.
- Formato de archivos cambiados y `git diff --check` correctos. `format:check` estándar detecta 162 archivos anteriores con finales CRLF; el mismo chequeo con `--end-of-line auto` pasa globalmente. No se normalizan archivos ajenos ni se cambia la configuración.
- Edge comprueba permisos visibles FARMER/ADMIN, alta con seis sensores, error 503 sin reenvío, secreto no persistido, conservación de clave al refrescar inventario, cancelación/habilitación, edición y archivo lógico preservando una lectura; también conserva las regresiones anteriores.
- Las bases temporales se eliminan al terminar. El simulador solo se ejecuta dentro de pruebas aisladas, no contra la base principal.
- Intento inicial de navegador: un login adicional agotó el presupuesto del endpoint de autenticación. La nueva prueba reutiliza la cookie de la sesión ADMIN del propio entorno de pruebas, sin elevar límites ni tocar seguridad productiva.
- Segundo intento: selector de origen sin nombre accesible exacto por incluir texto de opciones. Se añadió `aria-label`, no se ampliaron timeouts. Suite posterior correcta.
- Persiste la advertencia preexistente de consultas concurrentes de `pg`; no se cambian dependencias para ocultarla.

## Revisión manual al volver

1. Abrir http://localhost:4200/parcelas. Las nuevas acciones solo aparecen con ADMIN propietario. **No cambiar roles para probarlas sin autorización**.
2. Revisar primero los formularios y Cancelar, sin registrar hardware por accidente.
3. Para un alta autorizada: abrir inventario, escribir serie/origen/intervalo, confirmar y registrar. Guardar UUID y clave de forma privada antes de ocultar o navegar. No enviarlos por chat.
4. Revisar seis sensores y estado sin contacto: registrar no conecta físicamente el equipo.
5. Solo si procede: probar habilitación y cancelación; deshabilitar recepción no cierra válvula.
6. Editar una parcela propia; guardar y actualizar la lista.
7. **Archivar solo una parcela elegida explícitamente para ello**: escribir su nombre. No hay restauración desde UI.
